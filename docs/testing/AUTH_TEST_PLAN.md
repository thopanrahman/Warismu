# Rencana Pengujian (Test Plan) Black Box & White Box Autentikasi WarisMu

- **Proyek:** WarisMu — Asisten Edukasi & Simulasi Waris Islam (Faraid)
- **Cakupan Pengujian:** Siklus Penuh Autentikasi (Registrasi, Normalisasi Email, Verifikasi Email, Resend Verification, Login, Refresh Token & Rotasi, Deteksi Token Reuse, Logout, Lupa Password, Reset Password & Pencabutan Sesi, Proteksi Endpoint API, dan Rate Limiting)
- **Alat Eksekusi Rekomendasi:** Node.js Built-in Test Runner (`node --test`) untuk White Box API/Unit Test & Pengujian Fungsional Browser/HTTP untuk Black Box Test.

---

## 2. Rancangan Pengujian White Box (Unit, Jalur Cabang Logika, & Keamanan Internal)

Pengujian White Box memverifikasi jalur kode internal (*branch coverage*), kriptografi, transaksi database, dan isolasi data:

| ID Test | Modul / Fungsi Target | Jalur Logika yang Diuji (White Box Path) | Prosedur Pemeriksaan | Kriteria Keberhasilan |
|---|---|---|---|---|
| **WB-AUTH-01** | Normalisasi Email (`normalisasiEmail()`) | Jalur transformasi string: spasi awal/akhir, huruf kapital campuran, input `null`/`undefined`/non-string | Uji fungsi helper dengan input `"  UsEr+Tag@GMAIL.COM \n"`, `null`, `123` | Menghasilkan `"user+tag@gmail.com"` secara deterministik dan mengembalikan `""` untuk non-string tanpa melempar `TypeError`. |
| **WB-AUTH-02** | Validasi Batas Panjang Password (DoS Protection) | Cabang pemeriksaan `password.length > 72` sebelum `bcrypt.hash()` atau `bcrypt.compare()` | Panggil fungsi validasi password dengan string 73 karakter dan 10.000 karakter | Fungsi menolak input (`false` / HTTP 400) dalam waktu `< 1 ms` sebelum masuk ke fungsi `bcrypt`. |
| **WB-AUTH-03** | Hashing Token SHA-256 (`buatTokenAcak()` & `hashToken()`) | Verifikasi bahwa nilai `rawToken` tidak pernah sama dengan `tokenHash` yang disimpan di tabel `auth_tokens` dan `auth_sessions` | 1. Panggil generator token<br>2. Inspeksi nilai `token_hash` yang dikirim ke parameter query SQL `$1` | `rawToken` memiliki panjang 64 karakter hex (256-bit entropy, memenuhi `NFR-15`), dan `token_hash` di DB adalah digest SHA-256 yang berbeda dari `rawToken`. |
| **WB-AUTH-04** | Mitigasi Timing Attack pada `api/auth/login.js` | Cabang `if (!q.rowCount)` pada `login.js` tetap mengeksekusi `await bcrypt.compare(password, DUMMY_BCRYPT_HASH)` | Ukur selisih waktu eksekusi handler `login.js` antara email terdaftar (password salah) dan email tidak terdaftar | Kedua cabang mengeksekusi `bcrypt.compare` sehingga tidak terjadi pengembalian instan (< 5 ms) pada cabang email tidak ditemukan. |
| **WB-AUTH-05** | Atomisitas Transaksi Rotasi Refresh Token (`api/auth/refresh.js`) | Blok transaksi SQL `BEGIN` → `INSERT auth_sessions` → `UPDATE auth_sessions SET revoked_at, replaced_by_id` → `COMMIT` / `ROLLBACK` | Simulasikan kegagalan pada langkah `UPDATE` di tengah transaksi rotasi | Transaksi melakukan `ROLLBACK` penuh sehingga tidak ada refresh token yatim (*orphan active session*) yang tersimpan. |
| **WB-AUTH-06** | Verifikasi Algoritma Eksplisit JWT (`api/lib/auth.js`) | Cabang `jwt.verify(token, secret, { algorithms: ['HS256'] })` terhadap token dengan header `alg: "none"` atau `alg: "HS384"` | Buat token JWT dengan algoritma bukan `HS256` atau token yang sudah kedaluwarsa (`exp` di masa lalu) lalu panggil `penggunaDariPermintaan(req)` | `penggunaDariPermintaan(req)` selalu mengembalikan `null` untuk token non-HS256 atau token kedaluwarsa. |
| **WB-AUTH-07** | Interceptor Auto-Refresh pada `panggilApi()` (`src/lib/akun.js`) | Cabang `if (res.status === 401 && !opsi._sudahRefresh)` di `src/lib/akun.js` | 1. Panggil `panggilApi('/api/riwayat')` dengan access token yang sudah expired<br>2. Mock `/api/auth/refresh` mengembalikan access token baru<br>3. Verifikasi request `/api/riwayat` diulangi tepat 1 kali | Request asli diulangi otomatis dengan header `Authorization: Bearer <NEW_TOKEN>` dan tidak terjadi *infinite loop* jika refresh juga mengembalikan `401`. |
| **WB-AUTH-08** | Isolasi Data Riwayat Antar-Pengguna (`api/riwayat.js` — `NFR-18`) | Klausa `WHERE id = $1 AND user_id = $2` pada `GET`, `POST`, dan `DELETE /api/riwayat` | User A mencoba membaca (`GET ?id=UUID_B`) atau menimpa (`POST { id: UUID_B }`) sesi riwayat milik User B menggunakan JWT valid milik User A | `GET` mengembalikan `404 Sesi tidak ditemukan`; data milik User B di tabel `sessions` tidak berubah sedikit pun. |
| **WB-AUTH-09** | Isolasi Tabel `sessions` (Riwayat Chat) dari `auth_sessions` (Sesi Login) | Pencabutan seluruh sesi login saat Reset Password (`UPDATE auth_sessions ...`) | Jalankan Reset Password untuk User A yang memiliki 3 riwayat konsultasi di tabel `sessions` dan 2 sesi perangkat di `auth_sessions` | Kedua baris di `auth_sessions` berubah menjadi `revoked_at IS NOT NULL`, sedangkan ke-3 baris riwayat konsultasi di tabel `sessions` **tetap utuh 100%**. |
